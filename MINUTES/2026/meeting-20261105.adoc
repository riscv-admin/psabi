== Shadow stack save/restore libcalls

Sam: No longer proposing changing names, someone pointed out we'd need to change everything in libunwind too. Now just proposing marking them. Also proposing adding a software shadow call stack property. +
Kito: GCC has received a patch in the last week to add software shadow stack support, so may support that in the next release. +
Sam: On the LLVM side, next step is agreeing what the runtime does. Probably some more work for musl/glibc, but want to make it work on the embedded side. Someone at Global Foundries is also interested. Proposals on LLVM Discourse to make it more complicated, but proposer has accepted doesn't win you much, so accepted next steps are working on markings and runtime, not add more routines for probing, overflowing shadow call stack space, etc. So not getting much more complicated.

== LP64E

Craig: GCC and LLVM both implement an LP64E ABI, but not documented in the psABI. GCC will emit a deprecation warning if you try to use it. Think they also disagree on how to implement variadic arguments. +
Kito: Palmer filed a PR for it a few years ago, but work stalled. +
Sam: Also not sure of the state of ILP32E. +
Kito: Have this note. +
Sam: Not sure quite what subject to change means. Is that experimental? Now we have definitely-experimental ABIs, probably worth labelling them as such, like big-endian. May then open the door for LP64E as experimental. +
Craig: Do we have a list of what the corner cases are? +
Kito: Don't have a concrete list. Should start collecting that. +
Craig: On LP64E should we make GCC and LLVM match? +
Jessica: Assume everyone agrees they should match, question is which is right? Presumably step zero is to write down what those disagreements are. +
Craig: Issue is passing int128 to a variadic function. For normal RV64, we give it 16 byte alignment and so pick an even/odd register pair. Under EABI for RV32 with equivalent int64, stack alignment is used which is only 4, so doesn't use an even/odd pair. Rule also there for int128 on RV64 automatically due to its 8 byte stack alignment, but LLVM doesn't do that, because it decides it based on RV32E, not stack alignment, so missed. +
Jessica: Related question of whether we should even keep the 8 byte stack alignment. Not convinced it's worth it. +
Craig: Should document this.
